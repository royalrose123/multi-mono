1. 背景與目標

結論：用 Next.js 官方的 Multi-Zones，把 order 與 invoice 兩個 Next 15 App Router 專案組成同一個網站。兩邊各自 build、各自部署；Menu、設計系統與登入狀態共用。代價是跨 zone 換頁一律整頁載入。

需求：

  • 兩個獨立的 Next 15 App Router 專案（order、invoice），使用者看到的是同一個網域。
  • 各自上線：只改 invoice 就只部署 invoice。
  • 共用 Menu：兩邊的 Menu 一致，改選單內容最好不用部署任何 app。
  • 共用登入：在 order 登入，進 invoice 也是登入狀態。

demo 範圍：不做真正的認證、資料庫、i18n，也沒有實際部署到 Azure（只寫對應表與 CI 範例）。

2. 選型

結論：在「獨立部署」與「完整 App Router 能力（SSR、RSC）」都不能放棄的前提下，可行的只剩路徑分流類的做法；其中 Multi-Zones 設定最少、官方支援，所以採用。Monorepo 用 pnpm + Turborepo、共用套件用 JIT packages、路由層先用 order 的 rewrites。

2.1 十種做法比較（以 Next 15 App Router 為前提）

做法App Router / RSC獨立部署跨站跳頁體驗改動成本結論
Multi-Zones（rewrites）完整可跨 zone 整頁載入低採用
Vercel Microfrontends完整可整頁載入，有 prefetch 優化低綁定 Vercel；正式環境在 Azure，不採用
Reverse Proxy / Gateway（Nginx、Front Door）完整可整頁載入中本質同 Multi-Zones，是正式環境可替換的路由層（見 2.6）
Monorepo 合成單一 app完整不可最佳（全站 soft navigation）中高違反「各自上線」，不採用
npm 套件（host 引入另一邊）部分要連動發版好中實際上變成單一 app，不採用
Module Federation（nextjs-mf）不支援 App Router，已淡出可好高不採用
qiankun / single-spa / wujie與 SSR / RSC / router 衝突可好高不採用
Web Components無 SSR可好中只適合嵌入 widget；本 demo 的 runtime Menu 就是這個做法的對照組
iframe各自完整，但被框住可差（高度、網址、焦點、SEO）極低不採用
ESI / Fragment實驗性，hydration 難可視實作高不採用

另外討論過：Native ESM + import maps（瀏覽器直接 import 遠端 ESM，共享依賴要自己處理）與 Webpack Module Federation（remoteEntry.js + shared singleton 版本協商）。兩者在 App Router 下都只能在 client 端嵌入，而且無法共用 Next 內建的 React（App Router 使用 vendored React，見 2.4）。

2.2 三選二：獨立部署 / 一致體驗 / 完整 Next 能力

結論：三者最多同時拿兩個。本專案選「獨立部署 + 完整 Next 能力」，放棄跨 zone 的 soft navigation。
組合代表做法犧牲
獨立部署 + 完整 Next 能力Multi-Zones、Reverse Proxy跨 zone 整頁載入
一致體驗 + 完整 Next 能力單一 app（monorepo 合成）獨立部署
獨立部署 + 一致體驗Module Federation、qiankun、Web ComponentsSSR / RSC

根本原因：App Router 的 React、router 與 RSC 都在 build 時綁進整個 app。兩個分開 build 的 app 沒有共用的 router 狀態，也就不可能在它們之間 soft navigation。

2.3 Monorepo ≠ 單一 app

結論：Monorepo 只決定程式碼放在哪裡；部署單位由 app 的數量決定。本專案是一個 repo、兩個 app、兩個部署單位。
  • 共用套件在 build 時被複製進每個 app。所以改共用元件，所有用到它的 app 都要重新部署，這和用不用 monorepo 無關：拆成兩個 repo + npm 套件，一樣要升版、再各自部署。
  • Monorepo 的價值：一個 PR 改完兩邊、版本一定一致、CI 用 turbo --affected 自動判斷要部署哪些 app（見 6.4）。

2.4 React 18 與 App Router

結論：App Router 一律跑 Next 內建的 React 19，app 自己裝的 React 版本不影響。所以兩個 app 都裝 React 19（19.3.1），讓測試、型別與實際執行一致。

2.5 Monorepo 工具：共用套件的形式

結論：採用 pnpm workspace + Turborepo，共用套件用 Just-in-Time（JIT）packages：套件直接匯出 TypeScript 原始碼，由各 app 的 transpilePackages 編譯。
方案做法優點缺點什麼情況改用
JIT packages（採用）exports 指向 src/*.ts；app 設 transpilePackages沒有 build 步驟、改了直接 hot reload、設定最少每個 app 各自編譯一次；不能直接發佈 npm；套件的編譯行為跟著 app 的設定走現況：2 個 app、套件不對外發佈
Compiled packages套件用 tsc / tsup 輸出 dist，app 吃編譯後產物Turborepo 可快取套件 build；可發佈 npm；app 的 build 較快dev 要跑 watch；多一層 build 與 sourcemap 設定套件要發佈給 repo 外使用，或 app 數量變多、build 時間成為瓶頸
Nx以 project graph 管理任務，plugin 生態generators、module boundary 規則、分散式快取、多語言較重、學習成本高、設定與 plugin 綁定多團隊、多 app，需要強制模組邊界或非 JS 專案也要一起管

本 demo 例外：runtime Menu（apps/order/menu-runtime/）用 Vite library mode 打包成單一 ESM 檔，輸出到 order 的 public/menu-runtime/，因為它要在瀏覽器端用 import() 獨立載入，不經過 Next 的 build。它屬於 order，隨 order 部署。

2.6 路由層

結論：demo 用 order 的 next.config.ts rewrites，本機與 Docker 設定相同、最少元件。正式環境可以換成 Azure Front Door，app 程式碼不用改（login 的 303 用相對路徑、middleware 依 x-forwarded-host 組網址）。
方案優點缺點適用
order rewrites（採用）不需要額外元件；本機 dev、Docker、正式環境同一套設定invoice 的流量都經過 order（多一跳，order 掛了 invoice 也進不去）；INVOICE_ZONE_URL 在 build 時寫死demo、zone 少、order 本來就是主網站
Azure Front Door邊緣路徑分流，兩個 app 對等；invoice 換網址只改 Front Door；附 CDN / WAF本機無法重現；要設好 RSC 請求不快取的規則；費用正式環境、在 Azure 上
Nginx（自管）彈性最大、可放在任何環境多一個要維運、要 HA 的元件非雲端或已有 Nginx gateway 的環境

3. 架構圖

結論：瀏覽器只跟 order（同一個網域）說話；/invoices/* 由 order 在 server 端轉發到 invoice。Menu 資料由 order 提供：order 每次請求直接讀掛進來的 menu.json，並開放 GET /api/menu 給 invoice 與 runtime Menu；runtime Menu 的 JS 也放在 order 的 public/。沒有獨立的設定服務。
  • 同網域 cookie：瀏覽器眼中只有 order 的網域，所以 order 設的 session cookie（path=/）也會帶到 /invoices/*，兩個 app 用同一個 AUTH_SECRET 驗證 JWT。
  • Menu 資料的來源：menu.json 只掛進 order。order 的 layout 直接讀檔（改檔立即生效）；invoice 經內網呼叫 order 的 /api/menu（Docker 為 http://order:3000/api/menu）並快取 60 秒；runtime Menu 在瀏覽器端讀同網域的 /api/menu，不需要 CORS。
  • runtime Menu 的 JS：由 order 的 build 先用 Vite 打包到 apps/order/public/menu-runtime/menu-runtime.js，隨 order 的 image 部署。invoice 的頁面也經 order 的網域載入同一個檔案（路徑固定為 RUNTIME_MENU_SRC）。

必要時可改用獨立 config-server：把 menu.json 與 runtime Menu 的 JS 放在 app 以外的服務（正式環境為 Azure Blob + CDN）。取捨：

  • 由 order 提供（本 demo 採用）：少一個服務；同網域，不用處理 CORS 與儲存體的讀取權限；改 Menu 內容仍不用部署（order 每次讀檔）。代價是 runtime Menu 的程式碼跟著 order 部署，order 掛了 invoice 也拿不到最新 Menu（會用備援）。
  • 獨立 config-server（Blob + CDN）：Menu 資料或 runtime 元件要完全獨立於 app 部署、或多個網站共用時才值得。代價是多一個服務、跨網域要設 CORS、Blob 預設不開匿名讀取。細節見 deploy/azure/README.md 的「必要時改用獨立 config-server」。

4. 實作重點

4.1 assetPrefix vs basePath

結論：invoice 只設 assetPrefix: '/invoices-static'，不設 basePath；頁面直接放在 app/invoices/。這是 Next 官方 Multi-Zones 文件的做法。

為什麼不用 basePath：依 Next.js 官方 Multi-Zones 文件，zone 應該用 assetPrefix 讓自己的 /_next/* 靜態資源不和主網站衝突，頁面路徑則直接用資料夾結構表達（app/invoices/…）。

assetPrefix（採用）basePath
影響範圍只有 Next 產生的靜態資源網址：/invoices-static/_next/…所有路由、next/link、router、public 檔都自動加前綴
頁面位置app/invoices/page.tsx 就是 /invoices，網址與檔案一一對應頁面放在 app/，網址由設定推導
跨 zone 連結寫完整站內路徑（/orders/1001）就對連到前綴外的路徑要額外處理，容易寫錯
public 檔要自己放在 public/invoices-static/自動帶前綴
// apps/invoice/next.config.ts（節錄）
const nextConfig: NextConfig = {
  // 依 Next 官方 Multi-Zones 文件：zone 用 assetPrefix（不是 basePath），頁面直接放在 app/invoices/。
  assetPrefix: '/invoices-static',
  output: process.env.BUILD_STANDALONE === '1' ? 'standalone' : undefined,
  transpilePackages: ['@repo/ui', '@repo/menu', '@repo/auth', '@repo/zone-inspector'],
  async headers() {
    // 經 order 轉發時原樣傳回，用來判斷「是誰回應的」
    return [{ source: '/:path*', headers: [{ key: 'x-zone', value: 'invoice' }] }]
  },
}

// apps/order/next.config.ts（節錄）
async rewrites() {
  return {
    beforeFiles: [],
    afterFiles: [
      { source: '/invoices', destination: `${INVOICE_ZONE_URL}/invoices` },
      { source: '/invoices/:path+', destination: `${INVOICE_ZONE_URL}/invoices/:path+` },
      { source: '/invoices-static/:path+', destination: `${INVOICE_ZONE_URL}/invoices-static/:path+` },
    ],
    fallback: [],
  }
}

4.2 ZoneLink 與路由表

結論：所有可能跨 zone 的連結都用 ZoneLink：同 zone 渲染 next/link（soft navigation），跨 zone 渲染一般 <a>（整頁載入）。
  • zoneForPath(path)：/invoices 或 /invoices/… 屬於 invoice，其他都屬於 order（/invoicesX 也屬於 order，有測試）。路由表只有這一份，Menu JSON 不重複標記 zone。
  • 為什麼不能全部用 next/link：next/link 會嘗試 soft navigation（prefetch、RSC 請求），但跨 zone 的目標不在本 app 的 route tree 裡。官方 Multi-Zones 文件要求跨 zone 連結用 <a>。
// packages/menu/src/ZoneLink.tsx
export function ZoneLink({ href, currentZone, children, ...rest }: Props) {
  if (zoneForPath(href) === currentZone) {
    return <Link href={href} {...rest}>{children}</Link>
  }
  return <a href={href} {...rest}>{children}</a>
}

4.3 共用 Menu（build-time）

結論：Menu 的內容是掛進 order 的 menu.json，元件是 @repo/menu，跟著 app 一起 build。order 每次請求直接讀檔、invoice 向 order 的 /api/menu 取得；改內容不用部署，任何讀取失敗都退回套件內建的備援 Menu，畫面不會壞。
// packages/menu/src/read-local-menu.ts（order 用，節錄）
export async function readMenuFile(file = menuFilePath()): Promise<MenuResult> {
  // 路徑在執行期才決定；告訴 bundler 不要追蹤
  const text = await readFile(/* webpackIgnore: true */ file, 'utf8')  // 失敗 → { ok: false }
  return validateMenu(JSON.parse(text))
}
export const readLocalMenu = async (file?: string) => toLoadedMenu(await readMenuFile(file))

// packages/menu/src/get-menu.ts（invoice 用，節錄）
export async function getMenu(url = process.env.MENU_CONFIG_URL): Promise<LoadedMenu> {
  if (!url) return fallbackMenu('未設定 MENU_CONFIG_URL')
  try {
    const res = await fetch(url, { next: { revalidate: 60, tags: [MENU_TAG] } })
    if (!res.ok) return fallbackMenu(`HTTP ${res.status}`)
    return toLoadedMenu(validateMenu(await res.json()))
  } catch (err) {
    return fallbackMenu(errorMessage(err))
  }
}
  • 共用邏輯：「zod 驗證 → 失敗就用備援」放在 load-menu.ts（validateMenu、fallbackMenu、toLoadedMenu），讀檔版與 HTTP 版都用它，不重複。
  • order 不快取：layout 每次請求呼叫 readLocalMenu()（讀 MENU_FILE，本機預設 <repo>/deploy/menu.json），存檔後下一次請求就是新內容。
  • GET /api/menu：order 的 route handler（dynamic = 'force-dynamic'），讀檔＋驗證，成功回 200 與 MenuConfig、Cache-Control: no-store；檔案不存在或格式錯誤回 503，不回備援資料，讓 invoice 與 runtime Menu 各自決定怎麼備援。
  • invoice 的快取：60 秒、tag menu。改 menu.json 後 invoice 最慢 60 秒生效；要立即生效就呼叫 invoice 的 revalidate API。
  • zod 驗證：href 必須是站內路徑；未知欄位忽略（為 expand / contract 預留）；version 是 literal(1)。
  • 來源標記：回傳 source: 'remote' | 'fallback'，工具列顯示，E2E 用它判斷是否走備援。
  • Revalidate API：只有 invoice 需要（POST /invoices/api/revalidate-menu），需 Authorization: Bearer <REVALIDATE_TOKEN>，成功時 revalidateTag('menu')。order 不快取，所以沒有 revalidate API。
  • feature flag：flags.menuV2 決定渲染 V1 或 V2 樣式，兩個 zone 讀同一份 JSON，所以會同時切換（E2E 驗證）。

4.4 登入

結論：JWT（HS256，8 小時）放在同網域的 httpOnly cookie session。登入用一般 HTML form POST + 303，不用 Server Action；redirect 目標一律經過 safeNextPath；invoice 的 middleware 必須用 publicUrl() 組網址。
  • 為什麼不用 Server Action：登入後的目標可能在 invoice。Server Action 的 redirect() 走 order 的 client router，跨 zone 會失敗。form POST 收到 303，瀏覽器整頁 GET 目標網址，不管目標在哪個 zone 都正確。
  • 303 的 Location 用相對路徑：前面是 order 直連、Docker 還是 Front Door 都不用改。
  • 保護頁面：兩個 app 各自的 middleware.ts（invoice 排除 /invoices/api/*，那裡用 token 保護），沒有有效 session 時 307 到 /login?next=…。

坑：x-forwarded-host。order 的 rewrite proxy 設了 changeOrigin: true（next/dist/server/lib/router-utils/proxy-request.js），invoice 收到的 Host 是 invoice 自己的位址 invoice:3001，原本的網域只留在 x-forwarded-host。middleware 若直接用 request.url 組 redirect，瀏覽器會被導到 invoice 自己的位址，而不是使用者看到的網域。

// packages/auth/src/public-url.ts
export function publicUrl(path: string, headers: Headers, requestUrl: string): URL {
  const req = new URL(requestUrl)
  const host = first(headers.get('x-forwarded-host')) ?? req.host
  const proto = first(headers.get('x-forwarded-proto')) ?? req.protocol.replace(':', '')
  return new URL(path, `${proto}://${host}`)
}

safeNextPath 只接受以單一 / 開頭的站內路徑。實作時在 code review 發現第一版有 open redirect：/..//evil.com、/.//evil.com、/a/..//evil.com、/%2e%2e//evil.com 通過了「開頭不是 //」的檢查，但經過 URL 正規化（dot-segment）後變成 //evil.com。修正為正規化後再檢查一次，並補上這四個測試：

// packages/auth/src/safe-next.ts
export function safeNextPath(input: unknown): string {
  if (typeof input !== 'string' || input === '') return '/'
  if (!input.startsWith('/') || input.startsWith('//') || input.includes('\\')) return '/'
  try {
    const url = new URL(input, BASE)
    if (url.origin !== BASE) return '/'
    const normalized = url.pathname + url.search + url.hash
    // 正規化（dot-segment）後可能變成 //host，需再檢查一次
    if (normalized.startsWith('//') || normalized.includes('\\')) return '/'
    return normalized
  } catch {
    return '/'
  }
}

4.5 其他 Multi-Zones 的坑

坑原因本 demo 的處理
/_next/image 不套用 assetPrefixinvoice 的圖片最佳化請求會打到 order 的 /_next/image不使用 next/image；需要時另設 rewrite 或改用 CDN 圖片
主 zone 的全站 header 也會套用到其他 zone常見的安全性 header 寫法是在 headers() 對 /(.*) 全部套用（例如 CSP、HSTS、X-Frame-Options）。order 是入口，這些 header 也會套到經 rewrite 轉發的 /invoices/* 回應，蓋掉 invoice 自己的同名 header；CSP 沒涵蓋 invoice 的資源時，invoice 頁面會壞二選一：刻意全站一致（order 的規則涵蓋 invoice 的需求，或改由 Front Door / gateway 統一加），或各 zone 各自管理（order 只對自己的路徑設，排除 /invoices、/invoices-static）。本 demo 的 order 沒有定義 headers()
order 不能有 app/invoices 或根層 catch-all 路由rewrites 放在 afterFiles：order 自己的檔案路由先比對，會把 invoice 的路徑吃掉order 沒有這些路由；README 列為規則

4.6 設計系統與導頁視覺化

  • @repo/ui：Tailwind v4 的 @theme token 放在 theme.css，元件為 Button、Card、Table、Badge、PageHeader。zone 主色由各 app 定義 --color-zone（order 藍、invoice 綠），一眼看出目前在哪個 zone。
  • @source：Tailwind v4 的自動偵測只掃 app 自己的檔案（並忽略 node_modules），共用元件用到的 class 不會被產生。各 app 的 globals.css 加 @source "../../../../packages";（路徑相對於該 CSS 檔）。
  • @repo/zone-inspector：畫面底部的工具列，顯示目前 zone、整頁載入時間（performance.timeOrigin）、soft navigation 次數、Menu 來源（remote / fallback / runtime），並可切換 build / runtime Menu。計數存在 module 層級變數：soft navigation 時 module 不重跑，整頁載入時自然歸零。E2E 就靠這些 data-* 屬性與 window 記號判斷是 soft 還是整頁載入。

5. Monorepo 共用元件 vs Web Component

結論：共用 Menu 有兩種做法。Monorepo 共用元件：Menu 是 monorepo 裡的共用套件 @repo/menu，order 和 invoice 直接 import，隨各自的 build 打包、部署。Web Component：Menu 包成 <runtime-site-menu>，用 Vite 打包成一個 JS 檔由 order 提供，頁面在瀏覽器載入後才掛上。

這個 demo 同時實作兩種是為了對照，實際專案選其中一種即可。程式碼與底部工具列中，前者稱為 build-time Menu、後者稱為 runtime Menu。

5.1 Monorepo 共用元件

Menu 和頁面在同一棵 React tree 裡，layout 直接使用：

// layout.tsx
<header><SiteMenu menu={menu} currentZone="order" user={user} /></header>
SiteMenu（Server Component，server 端渲染成 HTML）
├─ 品牌文字
├─ 每個項目 → 連結元件（client component）
│     └─ 同 zone → next/link ／ 跨 zone → <a>
│  └─ 子選單（hover 展開）
└─ 使用者區：已登入 → 名字＋登出 form ／未登入 → 登入連結
  • 渲染：整個 <nav> 在 server 端產生，頁面一到就有 Menu。
  • 目前頁面：連結元件用 usePathname() 判斷 active，加上 aria-current="page"。
  • 導頁：依目標路徑屬於哪個 zone 決定，同 zone 用 next/link（soft navigation），跨 zone 用 <a>（整頁載入）。
  • 樣式：Tailwind，和頁面共用同一套設計系統（例如 active 色 order 藍、invoice 綠）。
  • 部署：Menu 元件打包在每個 app 裡，改了 Menu 元件，order 和 invoice 都要重新部署。

5.2 Web Component

Menu 用 Vite 打包成一個獨立的 JS 檔（自帶一份 React），放在 order 的 public/menu-runtime/；app 的程式碼不 import 它。頁面上分成兩層：

layout
└─ Host 元件（client component，Next 的 React）
     └─ <div>
          ├─ 載入中：佔位框 ／ 失敗：錯誤提示
          └─ <runtime-site-menu>          ← 瀏覽器端動態建立的 Web Component
               └─ #shadow-root
                    ├─ <style>（Menu 自己的 CSS）
                    └─ 另一份 React 渲染的 Menu
  • 載入：Host 元件在瀏覽器端用 import('/menu-runtime/menu-runtime.js') 下載那個 JS 檔（同網域，由 order 提供），完成後建立 <runtime-site-menu> 放進頁面。server 端只輸出外框和佔位框。
  • 傳遞狀態：Host 把目前 zone、目前路徑、使用者、導頁函式設成元素的 property；路徑改變時再設一次。
  • 渲染：Web Component 開一個 Shadow DOM，用它自己的那份 React 渲染 Menu。
  • 目前頁面：它不在 Next 的 React tree 裡，不能用 usePathname()，改用 Host 傳進來的路徑判斷。
  • 導頁：不能用 next/link。連結是普通 <a>，點擊時攔截並呼叫 Host 傳入的導頁函式：同 zone router.push()（soft navigation）、跨 zone location.assign()。
  • 樣式：CSS 放在 Shadow DOM 裡，和頁面完全隔離；頁面的設計系統進不去，要自己維護一份。
  • 部署：改 Menu 元件只要部署 order（JS 檔在 order 的 build 時打包），invoice 不用部署。

6. 共用程式碼的變更流程

結論：先判斷改動屬於哪一類：改內容不部署；改元件兩個 app 都部署，大改用 feature flag 讓兩邊同時切換；改資料格式用 expand / contract 分三步。哪些服務要部署由 pnpm deploy:affected（Turborepo --affected）決定。

6.1 三種改動

改動範例要部署什麼做法
內容新增 Menu 項目、改文字不部署 app改 deploy/menu.json：order 立即生效；invoice 等 60 秒或呼叫 invoice 的 revalidate API
元件 / 樣式改 packages/menu、packages/uiorder、invoice 都部署小改直接部署；大改用 feature flag（6.3）
runtime Menu 元件改 apps/order/menu-runtime/只部署 orderorder 的 build 會重新打包 menu-runtime.js
資料格式改 menu.json 的結構兩個 app 部署兩次expand / contract（6.2）

6.2 expand / contract

  1. Expand：先部署能同時接受新、舊格式的程式（schema 用 union 或新欄位設成選填）。兩個 app 都部署完成前，JSON 不動。
  2. 切換：改 menu.json 成新格式（order 立即生效），再 revalidate invoice。
  3. Contract：確認兩邊都穩定後，再部署移除舊格式支援的程式。

只「新增欄位」時不需要 expand：schema 忽略未知欄位，舊程式會照常運作。反過來，若直接把 version 改成 2，還沒部署新程式的 app 會驗證失敗並退回備援 Menu（不會壞，但內容是舊的）。

6.3 menuV2 feature flag

兩個 app 的部署一定有時間差。大改時：先把 V1、V2 兩版元件都部署到 order 與 invoice（flags.menuV2: false，使用者看不到差別）；兩邊都上線後，把 menu.json 的 menuV2 改成 true 並呼叫 invoice 的 revalidate API：兩個 zone 讀同一份 JSON，幾乎同時切換（order 下一次請求就生效，invoice 在 revalidate 後生效）。出問題時把 flag 改回去即可回滾，不用重新部署。

6.4 部署時間差的三種處理

7. 部署

結論：每個服務一個 Docker image，用 turbo prune 只帶需要的套件、Next 用 standalone 輸出。正式環境對應到 Azure Container Apps + ACR、Azure Files（menu.json）、Key Vault。CI 用 path filter 讓每個 workflow 只在相關檔案改動時執行。

7.1 Docker

  • 兩個 image：apps/order/Dockerfile、apps/invoice/Dockerfile，都在 repo 根目錄 build。
  • 階段：turbo prune @repo/<app> --docker → 先複製 package.json 與 lockfile 跑 pnpm install --frozen-lockfile（吃 layer cache）→ 複製原始碼、turbo run build --filter=@repo/<app> → runner 只複製 .next/standalone、.next/static、public，以非 root 的 node 使用者執行。
  • order：build 腳本先 vite build -c menu-runtime/vite.config.ts 再 next build，所以 runner 複製的 public/ 已含 menu-runtime/menu-runtime.js（Dockerfile 會檢查檔案存在）。menu.json 以 volume ./deploy:/config:ro 掛入、MENU_FILE=/config/menu.json。掛整個資料夾而不是單一檔案，因為編輯器「寫新檔再改名」的存檔方式會讓單檔掛載失效。
  • compose：order 8080:3000 是唯一入口；invoice 只 expose: ["3001"]，MENU_CONFIG_URL=http://order:3000/api/menu。

7.4 NEXT_PUBLIC_* 在 build 時寫死

NEXT_PUBLIC_* 會在 build 時被內嵌進 client bundle。同一個 image 部署到不同環境時，瀏覽器拿到的仍是 build 當下的值。

本 demo 的做法：不使用 NEXT_PUBLIC_*。runtime Menu 的網址固定為同網域的 /menu-runtime/menu-runtime.js（@repo/menu 的常數 RUNTIME_MENU_SRC），各環境都一樣，不需要環境變數；其他設定（MENU_FILE、MENU_CONFIG_URL）都是 server 端的 runtime env。真正必須在 build 時決定的只有 INVOICE_ZONE_URL（rewrites）與 BUILD_STANDALONE。

7.5 多個 replica 的快取

  • invoice 的 Menu data cache 存在每個容器自己的檔案系統，revalidate API 只會清到收到請求的那一個 replica。order 不快取 menu（多個 replica 掛同一個 Azure Files share），沒有這個問題。
  • 需要全部 replica 立即一致：改用共享的 cacheHandler（例如 Azure Cache for Redis）。否則接受最多 60 秒的延遲。
  • 若之後使用 Server Actions，要設定固定的 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY（本 demo 沒有使用）。

8.2 正式上線前要補的項目

  • publicUrl() 沒有驗證 x-forwarded-host / x-forwarded-proto 的格式，格式錯誤會 500；正式環境應只信任來自自家 proxy 的值。
  • Menu 的 href 檢查沒有擋控制字元（例如 /\t/evil.com，瀏覽器去掉 tab 後成為 //evil.com）；menu.json 可遠端修改，應補上。
  • revalidate token 不是 timing-safe 比對。
  • /api/login 收到非 form 的 content-type 時回 500 而不是 400。
  • AUTH_SECRET 未設定時 middleware 會直接失敗（fail-fast），部署時必須注入。
  • RuntimeMenuHost 在 script 載入成功但沒有註冊元件時會一直停在載入中（沒有 timeout）；runtime Menu 不渲染子選單。
  • deploy-affected 的 --dry-run 判斷不驗證其他參數，打錯字會真的部署。

8.3 長時間執行的容器中 invoice 的 revalidate 可能不立即生效

現象：容器長時間執行並經過主機睡眠後，revalidate API 回 200，但頁面仍是舊 Menu，要等 60 秒的時間型過期才更新；重啟容器後恢復正常。在新建立的容器上無法重現。

影響範圍：只有 invoice。order 每次請求直接讀檔，沒有 menu 快取，也沒有 revalidate API。

讀 Next 15.5.28 原始碼確認的事實：

  • incremental-cache/file-system-cache.js 的 revalidateTag 只在 tagsManifest 還沒有這個 tag 時才寫入 Date.now()（if (!tagsManifest.has(tag))）。
  • 但 revalidation-utils.js 的 revalidateTags 也會呼叫每個已註冊 cache handler 的 expireTags；預設 handler（cache-handlers/default.external.js）每次都覆寫 tagsManifest，值是 Math.round(performance.timeOrigin + performance.now())。
  • fetch 快取讀取時用 isStale（tags-manifest.external.js）判斷：tag 的時間 ≥ 快取項目的 lastModified（快取檔的 mtime）才視為失效。

可能原因是 performance.timeOrigin + performance.now() 落後於檔案 mtime 使用的牆上時鐘（例如主機睡眠喚醒後）。當時沒有量到兩個時鐘的差距，原因未查明，只是假設。

實務上的處理：60 秒的時間型更新不受影響；重啟 invoice 容器即恢復。正式環境若遇到，可改用共享 cacheHandler（7.5），或在 revalidate 後檢查 invoice 的 Menu 是否真的更新。
